Notes on Claude Code Mastery

September 02, 2026·
  • AI

Recently read: Arpan Patel, “Beyond the Prompt: Claude Code”

Stuff I disagree with:

  • Getting Claude to fill CLAUDE.md with every mistake. Don't have AI add guardrails to itself. Keep CLAUDE.md minimal and stable, like the Claude Code team's example in the article.
  • Overusing other people's Claude Code skills without understanding them. Treat a skill like a library: understand it before importing it; decide whether to import, roll your own, or do without; know what happens behind the scenes.
  • Treating MCPs the same way. You're not just importing instructions; you're connecting third-party software, often with credentials and access to local or remote systems. Much larger supply-chain/security surface.
  • Installing a language server plugin. Most LSP plugins add noise and bloat context. A post-edit lint hook is often enough. Or nothing—the models are pretty good at linting, formatting, and testing their changes.

Takeaways:

  • /goal — Claude's Ralph loop: keep running until a stop condition is met. According to the article, released May 2026. Missed it; haven't used it much—been playing around with Pi.
  • CLAUDE.local.md — uncommitted CLAUDE.md; have been wondering how to do that properly. Useful, but it doesn't follow fresh clones, other machines, or worktrees by default. Not a full solution.

Other notes:

  • Never used /compact, or hit the context window limit. Instead, I have Claude save a WIP file and resume later. Compaction, except in a real file: inspect it, edit it, or ask Claude to focus it on specific areas.
  • I don't commit WIP files. They may contain secrets or other transient/sensitive information.

Save the current working context to a <problem_name/task_name>.WIP.md file.

Focus on the current issue we're handling. Include important details from the conversation history, codebase exploration, debugging, work done, etc. as additional context—to save time when picking up this thread of work again. In particular, note which commands/scripts to run to debug, test, probe, or troubleshoot.

We might be coming back to this issue after a long period of time and may not remember most details, so be careful when noting things done.

There's no need to gather additional context. Start by planning out the document structure. The WIP document is intended to be append-only.

On project skills:

Project skills have always sounded useful, but in practice I've never had a reason to reach for them. If it's a common codebase pattern, good models can generally pattern-match from existing code. If it isn't, why add a skill for it?

Rare but important procedures are different. They belong in README.md or other human-readable codebase docs, and should usually be scripts—not free-form LLM delegation.

Then there's drift. Maybe the sweet spot is a pattern not self-evident from the code, with a skill filling the gap? If so, I haven't found it. Maybe I should experiment more.
